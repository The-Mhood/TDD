# ADR-0109 — Accelerated execution model & planning baseline v2

- **Status:** Proposed (owner ratification at P-01, DECISION_RATIFICATION_REPORT TDD-PLAN-RAT-001; becomes Accepted with the ratification comment on Issue #1)
- **Date:** 2026-11-20
- **Owning agent:** Takeover Technical Lead (enforces)

## Context
The owner directed (2026-11-20 review pass): (a) fix document inconsistencies (milestone names, RRP G-02 AC count, reference-PC purchase timing); (b) replace the 13–14-month execution model with a credible 4–8-week accelerated plan — "Do not simply shorten the dates… Develop a credible accelerated execution model"; (c) preserve the quality bar and all accepted specifications (AC-01…31, frozen ADRs, narrative decisions, traversal/combat contracts), with scope adjustments explicit and owner-approved; (d) revalidate the reference-hardware proposal; (e) audit technical claims phrased as engine guarantees. This ADR records the resulting technical decisions. It changes **when and how** work executes — not **what** the accepted specifications require.

## Decision
1. **Accelerated execution model (ROADMAP v2.0) is the planning baseline:** 4–8-week window; **Checkpoint A at W4** (verified playable core: M1+M2 gates + combat vs dummy/1 archetype); **Checkpoint B at W8** (Chapter 1 release candidate within the approved scope). Milestones M0–M10 keep their names and ACs (dep map §2 is the authority: M7 = content integration, M8 = optimization/stability, M9 = full QA, M10 = packaging/release) and are reached earlier; ch. 2–8 are post-RC waves through the identical per-chapter gates.
2. **Scope ladder SA-1…SA-8** (ROADMAP v2.0 §5) is the only mechanism that changes in-window shipped scope; ratified as a batch at P-01. Mid-flight SA changes require new owner approval + a re-baselined WBS delta in the Friday report. Prohibited accelerators unchanged (Roadmap Rule 6): no test removal, no defect ignoring, no AC lowering, no unlabelled interim content in shipped builds, no optimization claims without profiling evidence.
3. **Reference PC — single authoritative purchase date: order at P-01 (Day 0).** Specification, cost tiers, alternatives, and the 1440p/60 validation procedure are TR-18. The machine arrives W1, is calibrated W2, and serves as the **Windows CI node from W2** (F-04). All earlier timings (T00 "Phase 3 entry"; TR-15 "M6 entry"; ROADMAP v1.0 "M2 exit"/"M5 entry") are superseded — they were correct only for the 13–14-month plan. The RTX 3060 Ti / 1440p@60 anchor is a **budget target, not a proven fact**, until TR-18's benchmark has executed.
4. **Pure-core verification convention (TR-19 T13):** all arbitration/policy/transition/condition/serialization logic is implemented as **UE-independent C++ with a thin UE wrapper** and is compiled + unit-tested in the agent workspace (g++ 12.2 verified present 2026-11-20; precedent: dodge math 18/18 host-compiled in-sandbox, TR-14). **ADR-0012 remains fully in force for all UE-dependent code** (agents cannot compile/run it; verification = daily Mac test train + Windows CI). A UE header inside a pure file is a merge-blocking contract violation.
5. **Daily integration & evidence protocol (ROADMAP v2.0 §4.3):** feature branches only; two TL-reviewed merge batches per day (12:00/17:00); one daily owner Mac **test train** (60 min, one command: build + queued suites + gauntlets + auto-archived evidence + auto ledger row + auto one-line issue update); Windows CI per integration push from W2; Friday 8-point checkpoint report. Milestone-end integration is retired.
6. **Claim-classification convention (TR-19) is binding for all documents and reports:** [DS-G] design guarantee / [BUD] budget / [EN-V] engine behaviour (verify before citing) / [ST] status claim (dated citation) / [UNV] unverified (no claim permitted; reported as "to be verified by \<test\>"). The 15-claim audit (TR-19) corrected the v1.0 over-claims; notably: determinism of combat outcomes is a *verified design property within the same platform/build/test conditions* (cross-platform determinism is not claimed); "no penetration/no floating capsule" is assertion-enforced (T1), not an engine property.
7. **Research decisions D-19…D-25** (TRR) are recorded as the technical decisions of this pass and become binding with P-01 ratification (rendering stack + Metal look-dev level; PBR/PCG/Niagara, no custom shaders without ADR; ADR-0005 ratified with MM corpus-gated + Mover rejected; CMC sole capsule authority; single state machine + one damage pipeline + rule-computed outcomes; WP from first real slice + bounded Chaos; GLB exchange standard + no MetaHuman + canon validators).
8. **Verification resource model:** agent-side g++ (pure cores) / owner Mac (daily train, UE authority) / reference PC (Windows CI + all sign-off) — the three-surface distribution is what makes the fast-track credible; adding agent tracks beyond T1–T3 + TL does not increase throughput at this review/verification capacity (ROADMAP §4.4).

## Consequences
- **Positive:** verification loop shrinks from weeks to hours (daily, 3 surfaces); logic-layer work tests without the Mac; contract freeze makes 3-track parallelism safe; scope is explicit (SA register) so the schedule never hides cuts; claims are auditable (TR-19).
- **Positive:** the owner's daily 60-minute commitment and the Day-0 PC order become the project's two highest-leverage actions — both are named, scheduled, and risk-registered (DA-01, DA-03) rather than assumed.
- **Negative (accepted):** the in-window deliverable is a **Chapter 1 release candidate**, not the full 8-chapter game (SA-1); full delivery continues as post-RC waves at the same gates. If the owner requires more in-window scope, the window extends (re-baselined) — it is not compressed further without breaching the quality bar.
- **Negative (accepted):** the fast-track carries 10 new deadline-specific risks (DA-01…DA-10); the two dominant owner commitments (daily train, Day-0 PC + content team) are conditions of the plan's validity, not suggestions.
- **Reversibility:** this ADR is an execution-model decision. Reverting to a longer schedule = re-baselining WBS (no spec/AC/contract changes); individual technical decisions (item 7) reverse per their TRR entries (mostly high-reversibility pre-W5).
